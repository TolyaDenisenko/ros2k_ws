# Глава 14. Как мы проверяли и чему научились

Эта глава — не про конкретный пакет, а про **метод**: как проверять изменения в
симуляции, не мешая друг другу, как ловить ошибки в восприятии на сохранённых
данных, и список ловушек, на которые мы наступили (чтобы не наступать снова).

---

## 14.1. Изолированная симуляция: не мешать тому, кто уже работает

Две симуляции, запущенные на одном компьютере «как есть», **видят друг друга**: два
`/controller_manager`, два `/clock`, два вакуумных плагина на одних и тех же
топиках. В одном случае это привело к зависанию RViz у пользователя, пока шёл мой
тест. Решение — развести их по разным «сетям»:

```bash
export ROS_DOMAIN_ID=77          # ROS 2: ноды с разными domain id не видят друг друга
export GZ_PARTITION=claude_test  # Gazebo: отдельный «раздел» для топиков gz
ros2 launch cart_xarm_bringup arm_table_gz.launch.py headless:=true use_rviz:=false
```

* **`ROS_DOMAIN_ID`** — номер «домена» DDS. Узлы общаются только внутри своего
  домена. По умолчанию 0.
* **`GZ_PARTITION`** — то же для транспорта Gazebo.
* **`headless:=true use_rviz:=false`** — без окон: тест не открывает ничего на
  чужом экране. Для MoveIt для этого добавлен аргумент `use_rviz` в
  `xarm_moveit_config/launch/_robot_moveit_common.launch.py`.

Все команды проверки (`ros2 topic echo`, `ros2 action send_goal`) тоже выполняются
с теми же переменными, иначе они «постучатся» не в ту симуляцию.

> **Почитать.** [The ROS_DOMAIN_ID](https://docs.ros.org/en/kilted/Concepts/Intermediate/About-Domain-ID.html);
> [Gazebo transport: partitions](https://gazebosim.org/api/transport/14/envvars.html).

## 14.2. Сценарии проверки — короткие bash-скрипты

Типичный тест — скрипт, который поднимает изолированную симуляцию, ждёт, делает
действия и печатает результат, сверяя с **истиной из Gazebo**:

```bash
#!/bin/bash
cd ~/ros2k_ws && source install/setup.bash
export ROS_DOMAIN_ID=77 GZ_PARTITION=claude_test
timeout 1300 ros2 launch cart_xarm_bringup arm_table_gz.launch.py headless:=true use_rviz:=false > sim.log 2>&1 &
sleep 75                                                     # дождаться старта всего

# истинная поза объекта из Gazebo (PosePublisher -> /gz/object_pose)
P() { timeout 5 ros2 topic echo /gz/object_pose --field transforms 2>/dev/null \
      | grep -o "child_frame_id='$1'.*" | head -1 | grep -o "x=[-0-9.e]*, y=[-0-9.e]*, z=[-0-9.e]*"; }

ros2 topic echo --once /objects                              # что распознано
for id in box_flat_0 pick_box_0 cyl_tall_0; do
  n=${id%_0}
  echo "== $id (до: $(P $n))"
  timeout 300 ros2 action send_goal /pick_place xarm_grasping_msgs/action/PickPlace \
      "{object_id: $id}" --feedback | grep -E "success:|message:"
  echo "   после: $(P $n)"
done
grep -E "Traceback|\[ERROR\]" sim.log                        # ошибки нод
```

* Длинные тесты запускаются **в фоне** — пользователь может работать.
* «После» сверяется не с тем, что «думает» система, а с **Gazebo** — так ловятся
  ошибки, которые система сама не видит (например, объект «приварен» к руке и едет
  за ней).

## 14.3. Восприятие — на сохранённых кадрах, без симуляции

Каждый прогон pick & place — минуты. Ошибки распознавания проще ловить на
**сохранённых кадрах** облака: снять 6 кадров из позы наблюдения один раз и потом
сколько угодно раз гонять по ним `perception.py` с разными настройками. Так нашлось,
что плоская коробка в 1 кадре из 6 выходит цилиндром, и подобран новый признак формы
(глава 10, рис. 10.5): на 30 выборках было 14/30 → стало 29/30.

Один такой кадр лежит в книге: [`img/data/frame_observe.npz`](img/data/frame_observe.npz)
(80 тыс. точек в `link_base`), по нему построены все рисунки
([`img/make_figures.py`](img/make_figures.py)). Пример использования — глава 10, 10.12.

Ещё проще — **синтетика**: сгенерировать облако «стол + коробка 10×5×5 под 30° +
цилиндр» с шумом σ = 5 мм и проверить, что алгоритм возвращает известный ответ. Но
синтетика не ловит всего: высоту на реальном облаке завышала воксельная сетка, а на
синтетике всё было идеально.

## 14.4. Ловушки, на которые мы наступили

|---|---|---|---|
| Облако идёт (topic hz 7 Гц), а нода его не получает | QoS `BEST_EFFORT` + облако 32 МБ: одна потерянная UDP-часть — всё сообщение потеряно | подписка `RELIABLE` | гл. 10.2 |
| Нода падает: «logging filters cannot be changed» | устаревший `get_logger().warn()` — все вызовы из одного места | `warning()` | гл. 9.3 |

## 14.5. История с удержанием позы руки (для тележки)

Рука при езде тележки «уплывала» до упора сустава, и MoveIt отказывался планировать:
«Start state out of bounds». Проверка в изолированной симуляции показала: после
остановки тележки рука **не возвращалась** — никто не держал позу.

Причина в связке `JointTrajectoryController` + `gz_ros2_control`:

* контроллер захватывал два командных интерфейса: `position` **и** `velocity`;
* `gz_ros2_control`, если есть скоростная команда, исполняет **только её**;
* контроллер без PID-коэффициентов при удержании шлёт скорость 0 — без обратной
  связи по положению. Толчок сдвигает сустав, и он остаётся сдвинутым.

Решение — свой конфиг для симуляции
[`quasi_cart_description/config/xarm6_controllers_sim.yaml`](../../src/r2_robot/quasi_cart_description/config/xarm6_controllers_sim.yaml):

```yaml
gz_ros_control:
  ros__parameters:
    position_proportional_gain: 1.0   # скорость = 1.0 × (цель − текущее)
xarm6_traj_controller:
  ros__parameters:
    command_interfaces: [position]    # только позиция
```

В режиме `position` `gz_ros2_control` сам замыкает обратную связь: задаёт суставу
скорость, пропорциональную ошибке положения (П-регулятор). **Коэффициент
подбирали замером:** при 10 и 3 — тремор в покое (скорость суставов до 3.14 рад/с:
регулятор перерегулирует и раскачивается), при 1 — рука неподвижна и в покое, и
при езде.

> **Почитать.** [ros2_control: joint_trajectory_controller](https://control.ros.org/kilted/doc/ros2_controllers/joint_trajectory_controller/doc/userdoc.html),
> [gz_ros2_control](https://control.ros.org/kilted/doc/gz_ros2_control/doc/index.html);
> П-регулятор и автоколебания — [Wikipedia: Proportional control](https://en.wikipedia.org/wiki/Proportional_control).

## 14.6. Правила, которые из этого вытекают

1. **Сверяй с Gazebo, а не с тем, что система думает о себе.**
2. **Сначала воспроизведи, потом чини.** Каждая причина выше найдена замером, а не
   догадкой; две догадки (обрезка 5% «точно виновата», «камера не так висит») на
   проверке не подтвердились.
3. **Один источник правды.** Список объектов, правила классов, зоны — каждый в
   одном YAML; остальное генерируется или читается из него.
4. **Изолируй тесты** и запускай длинные в фоне.
5. **Пиши в лог, а не только в терминал**: трейсбек упавшей ноды должен остаться.
