# Распознавание объектов на OpenVINO

Как у нас устроено определение класса объекта по картинке: что поставлено, как запускать, что
измерено и что ещё не сделано. Платформа тележки — **Intel NUC**, поэтому движок — OpenVINO
(решение пользователя, 2026-11-02). Материал для выбора моделей и подходов —
[RECOGNITION_MODELS.md](RECOGNITION_MODELS.md), история решения в R2 —
[R2_OBJECT_RECOGNITION.md](R2_OBJECT_RECOGNITION.md).

> **Коротко.** Нейросеть находит объект на цветном кадре (рамка и название), облако точек даёт его
> положение, форму и размер. Кластер облака получает название рамки, если в неё попадает не меньше
> половины его точек. Геометрия всегда из облака, название по картинке идёт отдельным полем
> (`detector_label`). **Работает целиком, включая свою обученную модель** для четырёх форм сцены «рука
> на столе» (куб, параллелепипед, пластина, цилиндр). Рабочая модель — `sim_shapes_v3`
> (`model_fp16.xml`, порог `detector_conf:=0.2`): в сцене из 4 предметов названы верно 4 из 4, в
> нынешней сцене из 7 предметов (повторы `cube_2`, `cube_3`, `cylinder_2`) — 6 из 7; куб — самый
> неуверенный класс. Название используется командой «возьми куб 1» (`pick_by_name`) и уточняется
> осмотром с 5 ракурсов (`survey_objects`) — [PICK_PLACE.md](PICK_PLACE.md). Не проверено на настоящей
> камере и на тележке (NUC). Как модель делается — [MODEL_TRAINING.md](MODEL_TRAINING.md), как её
> улучшали (v4) — [RECOGNITION_IMPROVEMENT.md](RECOGNITION_IMPROVEMENT.md).

```mermaid
flowchart LR
    CAM["Цветной кадр<br/>/gripper_camera/color"] --> DET["openvino_detector<br/>(OpenVINO, ~6 мс)"]
    DET -->|"/detections<br/>рамки + названия"| OP["object_perception"]
    PC["Облако точек<br/>/gripper_camera/points"] --> OP
    OP -->|"/objects:<br/>положение, форма, label,<br/>detector_label"| NEXT["scene_manager,<br/>pick_place_server"]
```

*Кадр `/detections/image` из симуляции: рамки, названия и уверенность. Куб (0.29) — самый
неуверенный, поэтому для своей модели порог ставим 0.1–0.2, а не привычные 0.4.*

## 1. Что зачем

| Вопрос | Кто отвечает | Где в коде |
|---|---|---|
| Где объект, какой формы и размера | облако точек | `xarm_grasping/perception.py`, `object_perception.py` |
| Что это (какой класс) | нейросеть по картинке | `xarm_grasping/detector.py`, `openvino_detector.py` |
| Какой кластер какой рамке принадлежит | проекция точек в кадр | `perception.associate_detections`, `object_perception.py` |

## 2. Установка

OpenVINO ставится в отдельное окружение Python, системный Python не трогается:

```bash
python3 -m venv --system-site-packages ~/.venvs/openvino
~/.venvs/openvino/bin/pip install openvino
~/.venvs/openvino/bin/python -c "import openvino as ov; c=ov.Core(); print(ov.__version__, c.available_devices)"
```

`--system-site-packages` нужен, чтобы окружение видело `numpy`, `cv2` и пакеты ROS. Проверено:
OpenVINO 2026.4.1, Python 3.12, numpy 1.26.4 (системный, не обновлялся). На NUC — то же самое
(или пакет `openvino` из репозитория Intel).

Модели лежат вне репозитория: `~/.local/share/quasi/models/<имя>/`. Для первой проверки скачаны
готовые YOLOX (Apache-2.0, ONNX читается OpenVINO напрямую):

```bash
M=~/.local/share/quasi/models/yolox; mkdir -p $M && cd $M
for n in yolox_nano yolox_tiny yolox_s; do
  curl -sLO https://github.com/Megvii-BaseDetection/YOLOX/releases/download/0.1.1rc0/$n.onnx; done
```

Это модели на 80 бытовых классов COCO (кошка, чашка, бутылка, телевизор…). Модель называет
предмет только словом из этого списка. В нём нет «куба», «пирамиды», «цилиндра» и «пластины», то
есть тех форм, которые стоят на столе нашей сцены, поэтому назвать их она не может при любом цвете
и освещении (в лучшем случае случайно примет цилиндр за «бутылку»). Чтобы сеть узнавала наши
формы под их именами, её дообучают на своих картинках (см. §7).

## 3. Проверка без ROS

```bash
cd ~/ros2k_ws && source install/setup.bash
~/.venvs/openvino/bin/python -m xarm_grasping.detector \
    --model ~/.local/share/quasi/models/yolox/yolox_tiny.onnx \
    --image фото.jpg --device CPU --threads 2 --out /tmp/out.jpg
```

Печатает найденные объекты и время кадра. Размер входа берётся из модели.

## 4. Нода и запуск

`openvino_detector.py` читает кадр `image_topic` (по умолчанию `/gripper_camera/color/image_raw`) и
публикует:

| Топик | Тип | Что |
|---|---|---|
| `detections` | `vision_msgs/Detection2DArray` | рамки в пикселях кадра, `results[0].hypothesis.class_id` и `.score`; `header` как у кадра |
| `detections/image` | `sensor_msgs/Image` | кадр с рамками (только `publish_debug_image: true`) |

Параметры — `xarm_grasping/config/openvino_detector.yaml`: `model_path`, `model_type` (`yolox`; если
рядом с моделью лежит файл-спутник `<имя>.meta.json`, тип, классы и якоря берутся из него),
`labels_path` (`''` — COCO), **`device`** (`CPU | GPU | NPU | AUTO`), **`num_threads`**,
`conf`, `nms`, `max_rate_hz`. Нода работает на системном времени (`use_sim_time: false`), поток
`/clock` ей не нужен.

Запуск в сценарии «рука на столе». **Внимание:** по умолчанию (без `detector_model`) запускается готовая
YOLOX `yolox_tiny.onnx` (80 классов COCO) с порогом 0.4 — она наши формы не назовёт. Свою модель и порог
надо указать явно:

```bash
ros2 launch cart_xarm_bringup arm_table_gz.launch.py detector:=true

# своя модель на четыре формы; порог 0.2 вместо 0.4, потому что куб уверен слабее
ros2 launch cart_xarm_bringup arm_table_gz.launch.py detector:=true \
    detector_model:=$HOME/.local/share/quasi/models/sim_shapes_v3/model_fp16.xml detector_conf:=0.2
```

Аргументы `detector_model`, `detector_device`, `detector_conf` — в [RUN_SCENARIOS.md](RUN_SCENARIOS.md).

Launch запускает детектор интерпретатором `~/.venvs/openvino/bin/python` и включает в
`object_perception` параметр `detections_topic: /detections`. В `/objects` у каждого объекта
появляются поля `detector_label` и `detector_score` (пусто и 0, если рамка не нашлась).
Своё значение `label` (по правилам размеров) остаётся: от него зависит захват.

## 5. Как рамка находит кластер

Для каждого кластера облака точки переводятся в оптический кадр камеры и проецируются по
`camera_info` в пиксели. Рамка достаётся кластеру, если:

1. внутри рамки не меньше `detection_min_inside` (0.5) пикселей кластера;
2. рамка не больше `detection_max_area_ratio` (8) площадей кластера: иначе рамка «стола» или
   «кровати», накрывающая всё, забрала бы себе объекты;
3. рамка достаётся одному кластеру: пары берутся жадно по убыванию «доля внутри × score».

Рамки старше `detection_max_age` (3 с) не используются. Параметры — у `object_perception`.

## 6. Измерено (2026-11-02)

**Скорость на процессоре этого ПК (AMD Ryzen 5 3600, 6 ядер, AVX2),** кадр 640×480:

| Модель | вход | все ядра | 4 потока | 2 потока | 1 поток |
|---|---|---|---|---|---|
| `yolox_nano` | 416 | 9 мс (110 кадр/с) | — | — | — |
| `yolox_tiny` | 416 | 23 мс (43) | 31 мс | 46 мс (22) | 78 мс (13) |
| `yolox_s` | 640 | 68 мс (15) | 90 мс | 144 мс (7) | 272 мс (4) |

- Без ограничения потоков OpenVINO загружает все ядра: нода на `yolox_s` при 5 кадр/с брала
  ≈ 168% CPU. Поэтому в конфиге `num_threads: 2` и `max_rate_hz: 2`: предметы на столе стоят на
  месте, частые кадры не нужны. Дальше можно не считать непрерывно, а только по запросу.
- **Видеокарта NVIDIA через OpenVINO бесполезна:** он показывает GTX 1050 Ti как устройство
  `GPU` и работает на ней, но 550 мс на кадр против 66 мс на процессоре (его GPU-плагин рассчитан
  на графику Intel). На этом ПК использовать `CPU`. `GPU` и `NPU` имеют смысл только на NUC и
  проверяются там.
- Качество на фотографиях COCO: кошки 0.93, медведь 0.95, телевизоры и стулья находятся с
  верными рамками (`yolox_s`); `tiny` и `nano` теряют часть мелких объектов.

**Связка с облаком** проверена в симуляции «рука на столе» на 8 объектах прежней сцены (до замены набора на четыре формы): рамки, посчитанные
независимым путём из поз объектов (проекция углов габаритов через `camera_info` и TF), привязались
каждая к своему кластеру, перепутанных нет (соседние коробки в том числе). Модуль сопоставления
проверен также на синтетических случаях (две соседние коробки + рамка стола, смещённая рамка,
рамка в стороне, одна рамка на две коробки).

## 7. Своя модель: датасет, обучение, экспорт

Детектор понимает два типа моделей: готовую YOLOX (80 классов COCO) и свою SSDlite, которую мы
обучаем на кадрах из симуляции. Как это делается, с объяснением терминов («датасет», «веса» и так
далее) простыми словами и с графиками: [MODEL_TRAINING.md](MODEL_TRAINING.md). Тип модели SSD детектор
определяет по файлу-спутнику `<имя>.meta.json` рядом с моделью, так что новая модель подключается
одним аргументом `detector_model`.

Итоги нашей модели (`~/.local/share/quasi/models/sim_shapes_v3/model_fp16.xml`):

| Параметр | Значение |
|---|---|
| Классы | `cube`, `parallelepiped`, `rect_plate`, `cylinder` |
| Качество (mAP, проверочные кадры) | 0.945 |
| Скорость, процессор 4 потока | 6.4 мс на кадр |
| Размер файла | 4.5 МБ |
| В симуляции | 4 из 4 названы верно в сцене из 4 предметов (порог 0.2); 6 из 7 в сцене из 7 предметов |

Модель `sim_shapes_v4` (те же классы, обучена вплотную и со случайными цветами) лежит рядом, но
рабочей не стала: в живой сцене хуже узнаёт куб ([RECOGNITION_IMPROVEMENT.md](RECOGNITION_IMPROVEMENT.md)).

## 8. Чего пока нет

- **Модели для настоящих предметов и настоящей камеры.** Наша модель обучена на симуляции (идеальные
  однотонные предметы). На настоящей камере она не заработает без настоящих фотографий:
  [MODEL_TRAINING.md](MODEL_TRAINING.md) §16 (кадры камеры Orbbec, разметка, смесь с симуляцией).
  Модель R2 (`model.xml/.bin/.labels`, `model_objects.json`) на этом ПК отсутствует.
- **Проверки на NUC:** устройства `GPU`/`NPU`/`AUTO`, скорость, INT8.
- **Сегментация масок и позы по картинке** (для прозрачных пробирок): пока только рамки.
- **Запуск в сценарии тележки** (`cart_xarm6_gz` / навигация): пока только `arm_table_gz`.
- **Название по картинке в самом `/pick_place` не используется:** он берёт предмет по `object_id`.
  Название → номер предмета переводит `pick_by_name` («возьми куб 1»; верит нейросети при
  уверенности ≥ 0.3, иначе класс по размерам), а `survey_objects` уточняет название голосованием по
  5 ракурсам ([PICK_PLACE.md](PICK_PLACE.md)).
- **Слитые кластеры.** Если два предмета стоят вплотную и облако даёт один кластер, обе рамки
  попадают в него, а название получает одна (правило «рамка достаётся одному кластеру»). Разделения
  кластера по рамкам пока нет.
- (Сделано.) **Детектор-заглушка** из истины Gazebo: `detector:=stub` и `tools/stub_detections.py`.

## 9. Ловушки

- Нода и `python -m xarm_grasping.detector` запускаются интерпретатором окружения OpenVINO, а не
  системным `python3` (в нём нет `openvino`).
- Без `num_threads` одна нода съедает 150–170% CPU: не повторять эту ошибку на NUC, где процессор
  нужен ещё Nav2 и MoveIt.
- При сборке `pgrep -f` по имени скрипта находит собственную оболочку (CLAUDE.md, «Gotchas»).
